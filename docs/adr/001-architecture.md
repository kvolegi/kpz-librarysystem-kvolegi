# ADR-001: Вибір шарової архітектури (Layered Architecture)

## Статус

✅ Прийнято

## Дата

2026-05-11

## Контекст

Для проєкту **Library System** (Система управління бібліотекою) необхідно обрати архітектурний підхід, який забезпечить:

- Чітке розділення відповідальності між компонентами системи.
- Простоту тестування та підтримки.
- Можливість заміни окремих компонентів без впливу на інші.
- Відповідність принципам SOLID.
- Масштабованість для додавання нових функцій.

## Розглянуті альтернативи

### 1. Монолітна архітектура (без шарів)
- **Плюси:** Простота початкової розробки.
- **Мінуси:** Висока зв'язність (coupling), складність тестування, порушення SRP.

### 2. Мікросервісна архітектура
- **Плюси:** Незалежне масштабування, ізоляція збоїв.
- **Мінуси:** Надмірна складність для навчального проєкту, потребує оркестрації.

### 3. Шарова архітектура (Layered Architecture) ✅
- **Плюси:** Чітке розділення, простота розуміння, відповідність SOLID.
- **Мінуси:** Можлива надмірність для дуже маленьких проєктів.

### 4. Гексагональна архітектура (Ports & Adapters)
- **Плюси:** Максимальна ізоляція бізнес-логіки.
- **Мінуси:** Надмірна кількість абстракцій для навчального проєкту.

## Рішення

Обрано **шарову архітектуру (Layered Architecture)** з чотирма основними шарами:

```
┌─────────────────────────────────┐
│       API Layer (src/api/)      │  ← HTTP-ендпоінти, маршрутизація
├─────────────────────────────────┤
│   Service Layer (src/services/) │  ← Бізнес-логіка, валідація
├─────────────────────────────────┤
│ Repository Layer (src/repos/)   │  ← Доступ до даних, CRUD
├─────────────────────────────────┤
│   Model Layer (src/models/)     │  ← Доменні моделі, сутності
└─────────────────────────────────┘
         │
         ▼
   ┌───────────┐
   │  Database  │
   └───────────┘
```

### Опис шарів

| Шар | Відповідальність | Приклад |
|-----|-----------------|---------|
| **API** | Обробка HTTP-запитів, серіалізація/десеріалізація | `books_async.py` |
| **Services** | Бізнес-правила, оркестрація | `library_facade.py` |
| **Repositories** | Абстракція доступу до БД | `book_repository.py` |
| **Models** | Визначення сутностей та DTO | `book_builder.py` |

### Правила залежностей

1. Кожен шар залежить **тільки** від шару нижче.
2. API → Services → Repositories → Models.
3. Модель **не знає** про репозиторій, репозиторій **не знає** про сервіс.
4. Залежності інжектуються через конструктор (Dependency Injection).

## Відповідність SOLID

| Принцип | Реалізація |
|---------|-----------|
| **SRP** | Кожен шар має одну відповідальність |
| **OCP** | Нові функції додаються через нові класи, не змінюючи існуючі |
| **LSP** | Репозиторії реалізують спільний інтерфейс |
| **ISP** | Інтерфейси розділені за призначенням |
| **DIP** | Сервіси залежать від абстракцій, а не конкретних реалізацій |

## Наслідки

### Позитивні
- Легко писати unit-тести з моками для кожного шару окремо.
- Зрозуміла структура для нових розробників.
- Можливість заміни PostgreSQL на SQLite для тестів без зміни бізнес-логіки.

### Негативні
- Додатковий boilerplate-код для абстракцій.
- Потреба в ін'єкції залежностей.
